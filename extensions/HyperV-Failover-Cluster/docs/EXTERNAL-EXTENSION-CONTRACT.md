# CloudStack External orchestrator extension contract

## Evidence and scope

This is a **source-derived contract**, not evidence that a Hyper-V extension exists or has passed interoperability tests. It targets CloudStack fork commit `6fb6c184bca5ac3a18564292f129f9a10cf05a76`, branch `step7-native-sync`, and the checked-out reference `proxmox_adoption_registry/proxmox.sh`. The latter was read as a local working-tree file, not asserted to be a particular release. No lab or production calls were made. The 33 case-sensitive built-in action names below include four optional per-volume snapshot actions; separately, arbitrary registered custom actions are possible.

**Important feasibility finding:** the stated goal “no CloudStack changes for another orchestrator” is not met generically by this fork. Implementing a Hyper-V adapter **can** imitate several Proxmox-shaped wire values, but GUID-only native identities, natural Hyper-V topology, and native Hyper-V volume snapshots cannot be used transparently. Compatibility translations need durable, collision-free identities and a proof of safe semantics, not simple string substitutions. See §9 before declaring capabilities.

## 1. Process, envelope, success and failures

CloudStack executes an executable on the **management server**, not on the hypervisor: `executable ACTION /absolute/path/payload.json WAIT_SECONDS`. `ACTION` is a distinct argv item, not a shell command. The payload is UTF-8 JSON written to a fresh UUID-named file. For `wait == 0` Java substitutes `AgentManager.Wait`; it waits up to that many seconds and forcibly destroys the process and descendants on timeout. stderr is **merged into stdout**, and output is read only after process exit: keep both streams small and emit no diagnostic noise or secrets; otherwise JSON parsers may fail or a full output pipe can block the child until timeout. Child termination does not prove a remote WinRM operation was cancelled. [P:1442–1495,1600–1612]

`externaldetails` is a map of optional maps: `extension`, `resourcemap`, `host`, `virtualmachine`, and for registered custom actions `action`; `caller` is moved to the top level when present. Host details are filtered; extension and resource-map details are independently supplied. Configuration/credentials therefore have no universal Java-defined precedence. PR chooses host URL over extension URL, and host credentials over resource-map then extension credentials; do not assume that PR's keys (`user`, `token`, `secret`) apply to Hyper-V. Never log payloads, WinRM credentials, console tickets or signed URLs. [M:607–632,2181–2189; P:368–383; PR:53–71,125–131]

For an instance, Java normally supplies top-level `virtualmachineid` (CloudStack UUID), `virtualmachinename` (CloudStack internal instance name), and `cloudstack.vm.details` (serialized `VirtualMachineTO`). The latter includes `uuid`, `name`, `cpus`, `minRam` **bytes**, `enableHA`, `nics` and `details`; PR reads NIC `mac` and `broadcastUri` and divides `minRam` by 1,048,576 for MiB. Provider identity is not the CloudStack UUID. Cluster-only calls lack a VM TO. A pre-adoption `getconfig` has `externaldetails.virtualmachine.proxmox_vmid` but no CloudStack VM identity/TO. Parameters appear as top-level `parameters` when nonempty; registered/custom-action dispatch also adds top-level `action`. Ordinary built-in lifecycle dispatch does not necessarily add that property. Accept omitted optional maps, but fail closed for action-specific missing fields. [P:368–383,840–856; A:130–147; PR:72–118,1794–1799]

**Exit semantics:** exit 0 is process success, but not universal semantic validation. Many ordinary lifecycle callers simply trust exit 0; output parsers for particular actions add requirements below. For a native adopted operation **with a lease**, Java additionally requires parseable JSON with exact `status:"success"` before completing the lease. Return one compact JSON object with `status:"success"` for successful mutations even where Java is permissive. For errors return nonzero and a concise `{"status":"error","error":"..."}` with no secrets. Exit **90** means a known failure with no provider change: on a leased native operation Java abandons the lease. All other nonzero values, including **91**, mean uncertain outcome for a leased native operation and retain its fence; Java has no special numeric 91 branch. Timeout, invalid success JSON, lease completion failure, and post-submission exceptions also retain the fence. Outside leased native operations 90/91 are just nonzero failures; there is no automatic rollback guarantee. Reserve 90 strictly for provably unchanged provider state; use 91 as an extension convention for uncertain remote submission/outcome, not as a separately recognized Java protocol feature. [P:239–241,1452–1540,1554–1556; PR:480–496]

For all state changes, verify identity, power, current configuration and applicable pending state before changing anything; confirm the actual provider task and read the requested postcondition before success. An accepted remote task is not completion. A lost response or failed verification after a write is unknown, not permission to retry. Design idempotency per operation: verified absence may complete a removal, whereas blindly retrying create, reboot or snapshot creation can duplicate or change state. PR does not implement every safeguard equally; the detailed distinctions below are intentional. [PR:431–479,965–966,1026–1070,1083–1118; P:1474–1520]

These are extension **details**, string values rather than JSON booleans. Set to `true` only after every corresponding action and safe lifecycle has been implemented. `false`/absent means unsupported for these helper gates; discovery and storage explicitly require an enabled orchestrator and compare trimmed `true`, case-insensitively. Check full caller gates as well as the dispatch gate; no capability substitutes for safe implementation. [EH:37–77; D:50–71; SI:130–135; M:2327–2359]

### Draft metrics extension (separately coordinated Java work)

The draft `METRICS-CONTRACT.md` adds the host-envelope read-only actions `hoststats` and `vmstats`, gated by
`instancestatssupported`; that gate is not set by this extension. `hoststats` returns epoch `timestamp`, node CPU
percent, logical `cpus`, `total_memory_kb`, `free_memory_kb`, cumulative `network_rx_bytes`/`network_tx_bytes`, and
`load_average`. `vmstats` returns epoch `timestamp` and a `vms` map: `cpus`, `cpu_utilization`, `memory_kb`,
`memory_free_kb`, `memory_target_kb`, network RX/TX bytes, disk read/write bytes and disk read/write IOs. Unknowns
are JSON null. Native binding keys and name-drift rules are those in the draft; only this node's running VMs are
returned. Java computes deltas and handles counter resets. This is a draft extension to the source-derived baseline,
not a claim that the above cited historical fork supports these actions. The exact field sources, explicit disk
attribution limitation, and sanitized direct live results are in `DESIGN.md` under Read-only metrics.

## 4. Wire schemas: discovery and configuration

### `discover`

Example (IDs are JSON numbers, not GUIDs):

```json
{"status":"success","cluster":"cluster-a","instances":[{"vmid":101,"node":"node-a","name":"guest-a","type":"qemu","power":"running","template":false,"hastate":""}]}
```

Java requires exact cluster match; <=8 MiB text; `instances` array <=100,000; positive unique integral numeric `vmid` fitting Java `long`; `node` matches `[A-Za-z0-9][A-Za-z0-9.-]*`; `name`, `type`, `power` are strings; `type` is only `qemu` or `lxc`; power only `running`, `stopped`, `unknown`; template is boolean. Optional `hastate` is a string matching `[a-z-]{0,32}`, including empty. The `qemu`/`lxc` restriction is **not** generic: a Hyper-V adapter may use a compatibility token only if the deployment explicitly accepts its semantics. Snapshot is inventory, not write authorization. [D:76–104; PR:2401–2417]

### `getconfig`

```json
{"status":"success","identity":{"cluster":"cluster-a","vmid":101,"name":"guest-a","node":"node-a"},"power":"running","config_digest":"0123456789abcdef0123456789abcdef01234567","cpus":2,"memory_mb":4096,"agent_available":true,"nics":[{"device_id":0,"mac":"02:00:00:00:00:01","bridge":"switch-a","vlan":100,"ip_addresses":["192.0.2.10"]}],"disks":[{"device":"scsi0","storage":"shared","volume":"guest-a/root.vhdx","size_bytes":10737418240,"root":true}]}
```

Strict parser: <=1 MiB, one JSON value, duplicate object keys rejected at any nesting level, max nesting 64. All text identity and digest fields are nonempty, trimmed and control-character-free. `identity.vmid` is a positive canonical **JSON number**, not quoted; cluster+VMID must match the requested identity exactly. `power` is exactly `running` or `stopped`; `config_digest` is exactly 40 lowercase hex characters; `cpus` and `memory_mb` are positive canonical integral JSON numbers <= 2,147,483,647; `agent_available` is boolean. The digest is a stable configuration-version/change detector; Java does not specify a hashing algorithm for a synthetic provider token, but compares equality across reads and does **not** recompute it. Ensure it changes whenever relevant configuration changes; it cannot prove no A→B→A changes, incarnation identity or external mutation fence. PR reads its provider's 40-character config digest, rejects locked/pending configuration, rereads digest and power around guest-agent collection. [C:112–117,134–180,199–276; PR:2454–2480; R:212–217]

`nics` is required, may be empty to parser (native adoption additionally requires at least one); each object requires numeric nonnegative `device_id` (Java internally prepends `net`), unique device and case-insensitive unique colon MAC; `bridge` and `vlan` keys must exist and may be null, otherwise nonempty text and numeric VLAN 1–4094; `ip_addresses` is an array of distinct canonical IPv4 literals. `agent_available=false` and empty arrays represent missing agent evidence, not proof of no configured IP. PR filters loopback, link-local and non-unicast agent addresses; Java's getconfig parser itself only checks canonical IPv4 syntax. [C:182–196,277–307; A:227–230; PR:2487–2504]

`disks` is required; each is an object with unique `device` matching `(scsi|sata|virtio|ide)(0|[1-9][0-9]?)`. `storage` and `volume` are both absent/null or both nonempty strings; storage matches `[A-Za-z][A-Za-z0-9._-]*`, volume contains neither colon nor comma; unique `storage:volume` pairs. Optional `size_bytes` must be positive integral JSON number at most 18 digits; optional `root` boolean defaults false, at most one true. The parser allows zero roots and device-only legacy records, but volume accounting/adoption may leave such disks unrecorded. Return actual data-bearing disks; exclude CD drives. PR chooses root using first boot-order disk, legacy bootdisk, then first sorted disk. [C:308–350; PR:2505–2526; A:304–309]

## 5. Storage inventory, volume mapping and backing identity

```json
{"status":"success","cluster":"cluster-a","storages":[{"storage":"shared","type":"smb","shared":true,"enabled":true,"active":true,"total":1000000000,"used":400000000,"backing":"cifs/server/share","monitors":[]}]}
```

Java requires exact cluster match, <=1 MiB, array <=1000, unique storage names matching `[A-Za-z][A-Za-z0-9._-]*`, lowercase alphanumeric type starting a letter, `total` and `used` nonnegative JSON integers with <=18 digits, boolean shared/enabled/active, printable non-space ASCII backing 1–512 chars, and <=64 distinct monitors whose strings match `[A-Za-z0-9.:\\[\\]/_-]{1,255}`. The parser does not enforce used<=total. Two storages represent the same backing iff backing strings match **and** either both monitor sets are empty or their sets intersect; empty/nonempty is not equal. Provider-specific backing grammar is not enforced by Java. PR emits `rbd/[optional @cluster/]pool/data-pool/namespace`, `nfs/server/export`, `cifs/server/share`, `iscsi/portal/target`, or `type/@cluster/storage`; RBD monitor lists come from monhost. For another provider, define a stable collision-resistant backing namespace and use empty monitors unless semantically appropriate; do not claim sharing solely on equal labels. [SI:91–97,230–296; PR:2420–2450]

External primary pools are registered as `external://<storage name>` and identify existing orchestrator storage, not a request to create it. Disks map by exact provider slot and `storage:volume`, stored in CloudStack volume path; the slot is tracked as `externalSlot`. A change is recorded only after the callback; unknown outcome requires refresh, not blind compensating writes. PR fences with provider config digest, refuses snapshots or material pending changes, and checks slot+volume. Running changes require bus/hotplug support; the CD boot-order exception is narrowly defined, not blanket permission to ignore pending config. [plugins/hypervisors/external/src/main/java/org/apache/cloudstack/hypervisor/external/storage/ExternalPrimaryDataStoreLifeCycle.java:53–68; C:54–74; VSync:66; VO:58–61,138–149; PR:1083–1153,1178–1195]

## 6. ISO, waits, firmware and transfer objects

CloudStack uses `iso_path` if explicitly provided and matching `[A-Za-z][A-Za-z0-9._-]*:iso/[^,/]+`; otherwise it takes `iso_storage` from `resourcemap` then `extension` and constructs `<storage>:iso/cloudstack-<ISO UUID>.iso`. `fetchiso` first receives volume and optionally expected size with 300 s wait. If absent, Java requires a recognized checksum (MD5, SHA-1/224/256/384/512, tagged or inferred by hex length), obtains/reuses an HTTP(S) extract URL and sends it plus normalized algorithm/checksum with 3600 s wait. Such links **may** be signed/bearer URLs; treat all as secrets, validate TLS and never leak them. Success requires present=true. Own-file ISOs must already exist; do not download or delete them as CloudStack-owned copies. [VL:99–118,208–263,283–332,408–412]

`cdroms` at start/create is an ordered list of `{drive:<number>,volume:<string or empty>,bootable:<boolean>}`, up to four numbered from zero. It reflects CloudStack's recorded drives, and absent list means no synchronization. Running attach is a different action; a stopped instance gets its recorded CD state on next start. On ISO deploy `externaldetails.virtualmachine` gains strings `template_type:"ISO"`, `iso_os_type`, `storage`, `disk_size_gb`, `firmware` (`bios`, `uefi`, `uefi-secure`). `iso_os_type` is a Proxmox-style value such as `win11`, `win10`, `l26` or `other`, not a generic OS taxonomy. PR creates EFI/TPM state for secure UEFI; Hyper-V needs an independently verified equivalent and must reject unsupported firmware rather than silently downgrade secure boot. [VL:181–205,473–518; P:598–615,984–989; PR:1577–1594,1762–1793]

Other waits: discovery/liststorage/native pre-adoption config use 60 s; normal commands use supplied command wait or `AgentManager.Wait` fallback; disk move and disk-snapshot revert use `max(AgentManager.Wait,6900)`; ISO copy/check 3600/300; snapshot/disk lock acquisition uses 30 s; ISO per-instance attach lock 1 s. Native adopted operation accepts wait 1–6900 and checks lease remaining duration >= wait+30 before starting. Cluster snapshot-backup has its own supplied wait and is outside the new adapter's declared capabilities. [D:69–71; SI:209–213; A:131–137; P:259,1016,1037–1038,1452–1480; M:2361–2368; MI:132–135; VO:80–81; VL:116–117; VS:224–234,309–317]

## 7. Native adoption, identity and leases

Current Java authority keys are canonical provider cluster plus positive integer VMID; **node is placement, not part of the durable claim key**. VM details use `proxmox_vmid` and/or `External:proxmox_vmid`; aliases must agree. Host detail `proxmox_cluster` is the authority cluster, host `node` maps placement; VM's optional cluster detail must agree. A practical Hyper-V implementation therefore needs a durable, globally unique, non-reused integer-to-Hyper-V-GUID mapping scoped to the provider cluster, available to every management server and node, with a safe collision/incarnation story. Neither using a GUID directly nor hashing one to an integer without collision/reuse handling satisfies this Java contract. [P:260–288; R:129–151; A:153–169; plugins/hypervisors/external/src/main/resources/org/apache/cloudstack/hypervisor/external/adoption/README.md:3–8]

Native root-admin `adoptExternalInstance` defaults to dry-run. It reads `getconfig`, checks a unique mapped host for current node, both opt-ins, exact identity/noncollision, owner, external template, service offering CPU/RAM, NIC-to-owner-network mapping and quota. It can adopt Running **or Stopped**, recording disks where possible and noting unrecordable disks rather than rejecting the entire adoption. On actual adoption it serializes a sorted-key/no-whitespace manifest (CPU, `memory_mib`, name, networks with bridge/device/MAC/tag/CloudStack network UUID, ownership, placement cluster/node, status and numeric VMID), hashes exact UTF-8 manifest bytes with SHA-256, reserves the claim, imports the VM metadata without a provider create/start, removes `deployvm`, sets placement and imports NICs, binds UUID/internal name, re-reads provider config/power/node, activates the claim, and records accounting/volumes. Thus PR's older `prepare`/`create` bind and bound-start handshake is **not** the native import algorithm. [A:172–210,213–309,312–367; PR:859–865,1745–1750,1839–1851]

Java detects adoption if `adopt_existing` is `true` **or any** of `adopt_claim_id`, `adopt_claim_generation`, `adopt_manifest_sha256`, `adopt_manifest_json`, `adopt_execution_plan_sha256`, `adopt_ip_overrides_json` is nonempty. It validates claim/generation, matching cluster and numeric aliases, manifest bytes/hash/placement and CloudStack UUID/internal name. Never bypass the adopted path by clearing just one flag. For managed reads `status`, `getconfig`, `getipaddress`, `ListSnapshots`, operation is empty and Java validates managed state without a lease; `statuses` uses the separate status map. For mutations Java maps exact action to an allowed operation and acquires a durable lease before invoking the extension. [P:207–223,244–314,329–347; AR:135–150; PR:533–587]

Top-level `native_adoption_context` is manager-authored, never trusted from callers: `action`, `operation`, `authorization_from_state:"managed"`, `stored_state:"managed"` for reads or `"operating"` for leased operations, `claim_id` string, `generation` number, `cluster` string, `vmid` number, `manifest_sha256` string, `cloudstack_vm_ref` UUID string, `cloudstack_instance_name` string; leased calls additionally have `lease_id` UUID and numeric Unix `expires_epoch`. PR checks all against envelope and manifest, including unexpired lease, before provider access. The extension must not invent, persist, renew or complete the Java registry lease itself; Java completes or abandons it. Legacy PR has its own registry flow, distinct from native. The callback context is a scoped authorization assertion, not a reusable credential. [P:297–314,1455–1476; PR:533–577,337–416]

`getconsole` is leased as `console`; whole-VM snapshots map to `create_snapshot`, `restore_snapshot`, `delete_snapshot`; add/resize/delete/move disk, NICs, HA, scale, ISO attachment, `snapshotdisk`, `revertdisksnapshot`, start/stop/reboot/delete have their own operation names. Unknown action on an adopted VM fails closed. A lease is returned only on proven no-change failure or confirmed success; otherwise preserve it, inspect authoritative provider state and claim, and use the root-admin exact claim/generation/lease recovery procedure—never auto-replay. After successful native delete, claim is `retiring`; final release happens only after CloudStack VM absence is checked separately. [P:207–223,289–315,350–359,1496–1520; plugins/hypervisors/external/src/main/resources/org/apache/cloudstack/hypervisor/external/adoption/README.md:10–14,26–28]

## 8. Refresh and passive observation

`refreshExternalVirtualMachine` uses `getconfig` under the native lock, checks binding/name/host and expected power, re-fetches under the transaction, and compares digest, CPU and RAM before reconciliation. Fixed offering CPU/RAM drift is report-only; provider-only NICs import only when a unique matching eligible owner L2 network exists; missing native NICs are report-only. Periodic worker is opt-in globally **and per cluster**, defaults off, uses a database lock and skips uncertain identity/claims. [R:154–167,181–222,241–273; plugins/hypervisors/external/src/main/resources/org/apache/cloudstack/hypervisor/external/reconciliation/README.md:3–20]

Observation is a **separate collector-to-CloudStack API**, not an executable action. POST `submitExternalIpObservations` as a scoped root-admin-type API user with `hostid` CloudStack host UUID, canonical lowercase UUID `captureid`, and `observations` containing a JSON array string such as `[{"vmid":101,"mac":"02:00:00:00:00:01","ips":["192.0.2.10"]}]`. Each object has exactly those three keys; <=60000 UTF-8 bytes, <=256 rows, positive int32 numeric VMID, unique (VMID, normalized unicast nonzero MAC), 1–32 distinct usable unicast IPv4 strings. Empty batch means no observations, never clear. User→host→cluster sender mapping must already exist; cluster comes from the mapping, not request. Capture UUID is idempotent per host. Each source binding is rechecked, multi-IP conflict produces no candidate, and fallback needs two matching captures within 24 h, unchanged identity/host/NIC/network/bridge/VLAN binding, no usable agent IP and fresh revalidation before write. A sighting is not adoption or lifecycle authority. The PR node collector observes guest tap traffic for 60 s; Hyper-V needs a separately designed trustworthy equivalent, not a claim that WinRM guest data is packet-observer evidence. [OC:20–39; OB:27–32,48–92,103–140,147–189; OV:22–43; OR:141–184; plugins/hypervisors/external/src/main/resources/org/apache/cloudstack/hypervisor/external/observation/README.md:7–20]

## 9. Portability findings (Java hard-coding)

1. **Provider-specific durable identity names and integer namespace.** Native operations require `proxmox_cluster`, `proxmox_vmid`/`External:proxmox_vmid`, canonical positive integer and `int` parsing; Hyper-V VM GUIDs cannot be passed directly. [P:260–285; A:213–225,318–326]
2. **Registry data model and manifest are Proxmox-shaped.** Claim reservation validates numeric VMID and placement cluster/node, binding hashes and Proxmox-named columns; a GUID translation must remain durable across every server and migration. [AR:69–79,135–150,166–171; A:180–210]
3. **Discovery only accepts QEMU/LXC.** Hyper-V cannot describe its actual hypervisor type without Java changes or an explicitly documented compatibility alias. [D:83–95]
4. **Topology/placement are node and bridge/VLAN based.** Import maps `identity.node` to host `node`, uses `network_bridge` and VLAN; Hyper-V virtual-switch/trunk semantics do not necessarily have a bijective representation. [A:232–247,282–291; R:142–151,219–222,257–268]
5. **Synthetic config digest is restricted to a Proxmox-style 40 lowercase hex token.** Hyper-V must provide a stable change-sensitive compatibility token; hash equality alone does not provide provider incarnation fencing. [C:263–269; R:212–217]
6. **NIC and disk slot naming is provider-shaped.** Numeric NIC device becomes `netN`; disk slot regex only allows `scsi`, `sata`, `virtio`, `ide` plus 0–99; Hyper-V controller number/location and device identity require a stable lossless translation. [C:182–184,313–317; VO:138–149]
7. **Disk and primary storage identifiers mandate `storage:volume` and `external://<storage>`.** Hyper-V VHDX/CSV/SMB identities may need an unambiguous reversible mapping that is stable through moves and cannot contain colon/comma in the volume component. [C:71–74,319–327; plugins/hypervisors/external/src/main/java/org/apache/cloudstack/hypervisor/external/storage/ExternalPrimaryDataStoreLifeCycle.java:53–68; VO:138–149]
8. **ISO path and usage identity are provider-shaped.** ISO paths must be `<storage>:iso/<name>`; cleanup maps reported numeric `vmid` via Proxmox detail names, and OS types are Proxmox codes. [VL:103–104,221–241,381–405,430–439,473–487]
9. **Per-volume snapshots are Ceph/RBD specific.** Java gates on Ceph pool and passes Ceph client/keyring/tool settings and stores `volume@snapshot`; do not advertise for Hyper-V native checkpoints. [VS:77–85,123–136,160–175,249–271]
10. **Passive observations are integer-VMID and Proxmox-binding specific.** Receiver, DB join and resolver require positive int VMID plus host `proxmox_cluster`, `node`, `network_bridge`; GUID/Hyper-V-native switch identity needs mapping or Java changes. [OB:61–70; OR:89–93,141–152,175–184]
11. **Native status binding explicitly names provider identity.** `expected_proxmox_name` is supplied keyed by numeric VMID; extension must honor it even if provider is not Proxmox, and not mistake CloudStack name for provider name. [P:329–346; PR:2104–2133]
12. **Native custom-action dispatch is a closed allowlist.** Arbitrary extensions cannot add adopted-guest actions without Java changes; storage-only actions avoid this only when no adopted VM details are supplied. [P:207–223,244–258]

## 10. Implementation and verification gaps

* No Hyper-V/WinRM implementation, stable numeric-ID authority, switch/VLAN mapping, digest source, secure-boot translation or console bridge has been implemented or tested here. In particular, Hyper-V Generation 1/2, secure-boot templates, checkpoints with memory, CSV ownership migration and rollback behavior require provider-specific design and integration tests; the wire contract alone does not prove parity.
* Inspect the selected cluster's registered extension and exact source/version before implementation. Stock `extensions/HyperV/hyperv.py` is a useful basic WinRM example, not evidence of fork parity: it parses host `username`, `password`, `network_switch`, `vhd_path`, `vm_path` and basic VM TO, and its dispatch/actions do not implement this full contract. [extensions/HyperV/hyperv.py:43–71,115–288,291–323]
* Known source asymmetries: several Java lifecycle handlers accept exit 0 without parsing `status` or verifying provider state; stronger postcondition requirements in this document are safety requirements for the new extension, not checks performed by those handlers. PR accepts an uppercase provider digest on input but emits it unchanged; Java rejects uppercase digest output. A new adapter must output lowercase, and a mixed-case PR digest would fail the Java snapshot parser. [P:689–749,1041–1094; PR:2462–2465,2523–2526; C:267–269]
* Native lease recovery, cross-node GUID/integer mapping, `findiso` all-guest completeness, snapshot-mode/power semantics, and ambiguous remote WinRM tasks need explicit fake-transport and multi-process/SQL tests before enabling flags. No such tests were run in this source-documentation task. [P:1474–1520; PR:1628–1650,2354–2374]
